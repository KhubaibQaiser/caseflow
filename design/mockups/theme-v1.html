5 · Options compared

A · Icon button + menu, top-right Recommended

  • Same corner, same control, on every screen including login.
  • 2 clicks to switch, visible without leaving the page.
  • The familiar pattern (docs sites, GitHub, Vercel).

B · Theme inside an account menu

  • The shell has no account menu, so we would build one for a single preference.
  • 3 clicks and a hover submenu on desktop; hidden on login; submenus are poor on touch.
  • Buries the control we want people to find.

C · Better sidebar-footer control

  • Fastest on desktop (1 click) but only there.
  • Mobile still lives in the Account sheet, login has nothing, the rail needs a variant.
  • Three layouts for one setting; the footer stays crowded.

D · Icon that cycles on click

  • Same spot as A, but three clicks to reach a target and no way to see which options exist.
  • "System" is easy to miss, and a screen reader hears a changing value.
  • Rejected: A costs one more click and fixes both.

6 · Interaction spec

Icon logic: shows the theme in effect

PreferenceEffectiveIconaria-label
Systemlight (OS)sunTheme: System (light)
Systemdark (OS)moonTheme: System (dark)
LightlightsunTheme: Light
DarkdarkmoonTheme: Dark

The monitor icon appears only on the System row inside the menu. The trigger never shows it, so the glyph always matches what you see. Both svgs are in the markup and CSS shows one from data-theme or prefers-color-scheme, so server HTML is already right and nothing flickers. The same text appears in the tooltip (LazyTooltip, on hover and focus).

Menu semantics (Radix DropdownMenu)

  • DropdownMenu.Trigger is a real button with the aria-label above, aria-haspopup="menu", aria-expanded.
  • DropdownMenu.Label "Theme", then RadioGroup with three RadioItems (menuitemradio, aria-checked) and an ItemIndicator check.
  • Keys: Enter/Space/ArrowDown opens, arrows and typeahead move, Enter selects, Esc closes and returns focus to the button. Selecting closes the menu and applies at once.
  • Targets: 34px trigger (40px on mobile), 32px rows (44px on mobile). Focus ring is the shell's 2px accent outline.
  • Tab order: first control of the page's first row. On /login the email field takes focus on load.

Persistence (unchanged)

  • Cookie theme=system|light|dark, 1 year, SameSite=Lax; Path=/, plus Secure in production. Zod parses it on the server.
  • Root layout renders <html data-theme> from the cookie (none for System). The first byte of HTML has the right tokens and color-scheme, so no flash and no inline script. The strict nonce CSP stays as it is.
  • The menu handler sets the cookie and documentElement.dataset.theme. No fetch, no reload.

System when the OS changes

  • With no data-theme, CSS uses @media (prefers-color-scheme: dark). When the OS flips (sunset, a manual change), tokens and the icon swap live, with no JS and no reload. The cookie keeps saying system.
  • The only JS: a matchMedia listener, mounted while the button exists, refreshes the aria-label and tooltip ("System (dark)"). Server HTML renders "Theme: System" and hydration fills in the effective theme, to avoid a mismatch.
  • Light or Dark explicitly chosen ignores the OS entirely.

Where it lives in code

One ThemeMenu in components/shell, rendered once by the shared page header (desktop/tablet), the mobile top bar, and the login layout. The Account sheet and sidebar footer lose their theme code. The viewport.themeColor pair is unchanged.
